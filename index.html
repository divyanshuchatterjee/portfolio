The implementation was optimized for large enterprise payloads, with particular attention to traversal strategy, object creation and memory consumption. The design supports large FHIR bundles while keeping the validation pipeline extensible.

CASE STUDY · DISTRIBUTED PROCESSING

Multi-Pod Job Processing

A distributed scheduled-processing architecture for a Spring Boot service running across multiple Kubernetes pods, designed to process database-backed jobs concurrently without duplicate work.

KubernetesRuntime
PostgreSQLJob store
Multi-podParallel workers
AtomicRow claiming

Architecture

SchedulerPeriodic trigger
→
Pod AClaims available rows
+
Pod B / CClaims other rows
→
PostgreSQLFOR UPDATE SKIP LOCKED

The problem

  • The service runs as multiple Spring Boot pods in Kubernetes.
  • Each pod wakes up on the same scheduler interval and queries the job table.
  • Without coordination, multiple pods could select the same pending record.
  • Traditional locking could make workers wait on rows already being processed.

The solution

  • Used PostgreSQL FOR UPDATE SKIP LOCKED to atomically claim work.
  • Rows already locked by another worker are skipped instead of blocking.
  • Each pod receives a distinct set of available jobs.
  • Processing can scale horizontally by adding more Kubernetes pods.

How concurrent processing works

1Scheduler firesMultiple pods can trigger at the same time.
2Transaction startsWorker queries eligible pending records.
3Rows are claimedFOR UPDATE locks selected rows atomically.
4Locked rows are skippedOther pods continue with different available rows.
5Job executesClaimed work is processed exactly by its owning worker.

Why SKIP LOCKED?

It turns the database into a lightweight work-claiming mechanism. Workers do not need to wait for rows currently owned by another pod, which reduces lock contention and keeps available work moving through the system.

Scalability

The architecture is horizontally scalable: additional Kubernetes pods can process independent rows concurrently without introducing a separate distributed-lock service.

Engineering considerations

Atomic claimingDatabase row locking ensures that work ownership is established inside the transaction.
No duplicate selectionOnce a row is locked by one worker, concurrent workers skip it.
Reduced contentionWorkers do not block behind already-claimed rows.
Horizontal scalingMore pods can be added to increase processing capacity as workload grows.
